Step 1: Save Image + Job
Client: uploads an image

Server: (i) saves the image to disk (ii) saves the file path of the image to the database (iii)  records that a job exists

Files, such as images,  are not stored in the database – they are stored in the filesystem (disk) or object storage like Amazon S3

The database is for storing structured data only (structured and semi-structured), not unstructured data like images or videos.

Query JSONB Data
PostgreSQL provides us with special operators to work with JSON/JSONB
->  returns data as JSONB
->>  returns the data as TEXT

We use -> when we want to extract data that is fed into a pipeline

We use ->> when we want to display, compare or pass data to a function that expects TEXT

Query JSONB Data (1)

-- difference between -> and ->>
SELECT id, 
payload->'file_size' AS size_jsonb,    -- returns jsonb: 5242880
payload->>'file_size' AS size_text     -- returns jsonb: "5242880"
FROM jobs;
 

Query JSONB Data (2)

-- difference between -> and ->>
-- We use ->> when we need to do comparison
SELECT id, 
payload->>'original_filename' AS filename
FROM jobs
WHERE payload->>'mime_type' = 'image/jpeg';
 

Query JSONB Data (3)

-- difference between -> and ->>
-- We use ->> when we need to do comparison
-- there is no error if a field is missing
SELECT id, 
payload->>'original_filename' AS filename
FROM jobs
WHERE payload->>'source' = 'mobile_upload';

The Full Picture



Output Files

The client needs the path to the processed images

Let's assume we have four operations (convert to grayscale, apply a blur, scale to a standard size, generate a thumbnail)

Each operation produces a new file on disk. The worker need to keep a record of the location of each output file plus any failures so that the client can retrieve them during polling


Output Files

We will store the output files using JSONB since there is variability in the number of files

Workers write the results incrementally. The client should be able to get partial results (not wait for all four files to finish). JSONB allows us to append one field at a time

Errors (failures) will be plain text (TEXT)

Tracking Job State

We need a way to add a timestamp when the state of the job changes (updated_at). This becomes extremely important when the server want to send notifications to the user (SSE) instead of the using hammering the endpoint every second (polling)

Why: How do know if a worker has crashed? How do we know how, on average, it takes to create thumbnails?

We need to always know the state of the submitted job

The created_at column tells us only when the job was submitted (history)

Tracking Job State

Polling (client):
GET /jobs/status/{public_id}

Server Sent Events (SSE): 
   "Has this job changed since the last time I checked?" If
    yes, let me notify the client of this change

The updated_at Column

The application code (handlers) should not be given the responsibility of updating this column

The application  has many components that change things in the system, so our handlers would miss all these changes.  The DB should always be responsible for doing the updates

The updated_at Problem

If each component is responsible for updating the updated_at column, some components might forget to do so.  This is a database concern, not an application code concern

We use a trigger to do this critical task for us
 
A trigger fires on every update regardless of which part of the system wrote the query

The updated_at Problem

If each component is responsible for updating the updated_at column, some components might forget to do so.  This is a database concern, not an application code concern

Triggers

-- updated_at is updated by a trigger
CREATE OR REPLACE FUNCTION set_updated_at()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at = now();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER jobs_updated_at
BEFORE UPDATE ON jobs
FOR EACH ROW EXECUTE FUNCTION set_updated_at();
